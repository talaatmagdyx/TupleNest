Introduction

TupleNest is a local-first IDE for PostgreSQL and SQLite. It runs entirely on your machine, talks directly to your database (over the PostgreSQL wire protocol, or by opening the SQLite file), and stores credentials in your operating system's keychain. There is no account, no cloud, and no telemetry. Those are the two engines; no other is planned.

This page is a hub. Each section is a short, practical walkthrough; where a topic is broad, it links to the relevant Features or Security section for depth.

Installation

Download the build for your platform from the Download page, then:

  • macOS — open the .dmg, drag to Applications, then run xattr -dr com.apple.quarantine /Applications/TupleNest.app. macOS calls the unsigned app “damaged”; right-click → Open does not bypass that on macOS 15+.
  • Windows — run the installer; on SmartScreen choose “More info” → “Run anyway”.
  • Linux — chmod +x the AppImage and run it, or install the .deb.

Prefer to build it yourself? The build-from-source steps are on the Download page.

Create your first connection

Open the connection editor and pick the engine. For PostgreSQL, fill in host, port, database, and username. For SQLite, type the file's path or press Choose…; turn on Create a new file to make an empty database there on connect. Choose an environment (development, test, staging, or production) — production connections are shown distinctly so you always know where a query will run.

On a first launch a three-step tour walks through connecting, the safety model, and the assistant and MCP; after an update, What's new shows once. About opens either again.

Click Test to run a staged check (DNS → TCP → authentication) before you commit. When you save, the password goes to the OS keychain and the profile stores only an opaque reference.

New profiles default to verify-full TLS — they fail closed until you deliberately relax them.

Run your first query

Type SQL in the editor and press ⌘↵ (or Ctrl+Enter). Results stream into a virtualized grid below, with execution duration and true row count. The whole editor is sent as one statement; running only a selection is not supported yet.

Explore the schema

The left explorer lazily loads schemas, tables, views, functions, indexes, and constraints. Use global search (⌘P) to jump to any object, or open the ER diagram to see foreign-key relationships as a graph.

Connection profiles

Profiles group by environment and remember TLS mode, optional custom CA, SSH settings, and the keychain reference for the password — never the password itself.

TLS modes

Four modes: Disabled, Prefer, Verify CA, and Verify Full. In the verify modes, TLS is required and a plaintext server is refused. See the Security page for exactly what each mode guarantees.

SSH tunnels

To reach a database behind a bastion, enable the SSH section and provide the host, user, and private key path. Host keys are verified; a changed key is rejected rather than silently trusted.

If the private key is protected by a passphrase, enter it in the Key passphrase field. It is stored in the OS keychain like the database password, never in the profile. Leave the field empty for a key without one. A missing or wrong passphrase is reported straight away, before the SSH server is contacted.

Password storage

Passwords and SSH key passphrases are stored in the macOS Keychain, Windows Credential Manager, or the Linux Secret Service — never in a config file, and never returned to the UI layer. Details on the Security page.

SQL editor

Schema-aware completion, formatting, multiple tabs, query history, snippets, and parameter binding. The editor understands PostgreSQL literals (dollar-quoting, nested comments), which is what makes the safety guard reliable.

Result grid

Streaming rows, virtualized rendering, sorting by column, explicit NULLs, copy cell/row/selection, and export. Large results are bounded by row, byte, and per-cell limits, with clear truncation indicators. A result keeps 20,000 rows; a plain read (one SELECT, VALUES, TABLE or WITH … SELECT that writes and locks nothing) stops at the limit on the server instead of reading the rest, and the footer says "20,000+ rows (stopped at the limit)". Other statements run to the end.

Query plans

Run EXPLAIN on the current statement from the command palette. Toggle ANALYZE to execute it and get real timings, and BUFFERS to see which nodes read from disk. ANALYZE defaults on for a plain SELECT and off for anything that writes — it really runs the statement.

The plan is drawn as a tree. The node marked BOTTLENECK is where time is actually spent, measured as self-time: the node's wall time minus its children's. That matters because a Nested Loop or Gather often shows a large total that belongs entirely to a child.

What the badges mean

  • BOTTLENECK — most of the execution self-time is here.
  • DISCARDED n — the node read those rows and threw them away. Usually the strongest sign an index would help.
  • DISK SORT / SPILLED — a sort or hash exceeded work_mem and went to disk.
  • HEAVY READ — blocks came from disk rather than cache, so the query is I/O bound.
  • n LOOPS — the node ran that many times; a hash or merge join may beat repeating it.
  • EST ×n OFF — the planner's row estimate missed by that factor; statistics may be stale.
  • NEVER EXECUTED — the executor short-circuited that branch.

Candidate indexes

Under the statistics, the panel lists Candidate indexes: runnable CREATE INDEX statements derived from the filters in the plan, each with a copy button and a line saying which node earned it. Columns are ordered the one way a btree can use them — every equality column first, then a single range column, because an index cannot narrow any further once it passes the first range boundary.

Filters a plain column index cannot serve get an expression index instead: lower(email) = … yields CREATE INDEX ON t ((lower(email))). The expression is reproduced character for character, because PostgreSQL only uses an expression index that matches the query's expression exactly.

You will see nothing at all in several cases, and that is deliberate:

  • An OR between predicates — the planner wants a separate index per branch, not one composite.
  • A join condition (column against column), an inequality, or an expression over more than one column.
  • Anything CREATE INDEX would reject. Index expressions must be IMMUTABLE, and volatility depends on the argument type: date_trunc('day', ts) is immutable on a timestamp but stable on a timestamptz, which reads the session time zone. TupleNest checks the column's real type before offering one.
These are candidates to verify, not promises. The advisor reads the plan's filter, not the table's data distribution — an index on a column that is 90 % one value helps nothing. Build it, re-run EXPLAIN, and confirm the scan changed. Remove it with DROP INDEX if it did not.

Time outside the plan

JIT compilation and trigger time are reported separately by PostgreSQL and belong to no node, so a statement can spend most of its runtime somewhere the tree doesn't show. Both appear in the statistics panel when present.

On a parallel plan, PostgreSQL reports one “loop” per worker and those workers run concurrently. TupleNest divides them back out, so self-times sum to the execution time rather than exceeding it.

Plans can be exported as JSON (which pev2 and explain.depesz.com both read), as an indented text tree, or as Markdown.

Analysing a plan you didn't run

You can analyse a plan from anywhere — psql on another machine, a ticket, a colleague's message — without connecting to anything. Open Analyze a pasted plan from the activity rail (the clipboard icon) or the command palette, paste, and press ⌘↵.

Both formats work: the indented text psql prints, and FORMAT JSON. TupleNest detects which as you type and says so before you press anything; text it doesn't recognise is called out rather than drawn as a misleading tree. Everything else — the badges, the self-time bars, the insights — behaves exactly as it does for a query you ran here.

The plan is read on your machine. Pasting a plan into a website means sending table names, index names, filter conditions and sometimes literal values from production to a third party; this exists so you don't have to.

Comparing two runs

Run a query, change something, run it again, then open Compare EXPLAIN plans from the command palette. Above the fold are the whole-query numbers — time, cost, and any node type that appeared or vanished. Below them, Node by node lines up the two trees and reports each node's own delta, so you can see which one absorbed the time rather than only that the query got slower.

Nodes are paired by type, relation and index name. One with no counterpart is marked new or gone rather than matched to something it is not, and a change is only called slower or faster past both a 1 ms and a 10 % floor.

Where two siblings look identical — an Append over matching partition scans — only their position separates them, and position is not evidence. Those rows are labelled ambiguous. Treat their deltas with suspicion; the label exists because guessing silently is how a previous release put the bottleneck badge on the wrong node.

Generating a migration

In Schema diff, compare two schemas and press Generate migration. You get the ALTER statements the difference implies, each tagged with what it will cost you:

  • safe — additive and reversible: a new nullable column, dropping a NOT NULL.
  • review — it will run, but the outcome depends on your data: a type change rewrites the table and holds an ACCESS EXCLUSIVE lock; adding NOT NULL fails if any row is null; a new table has no keys or indexes because a column diff does not carry them.
  • destructive — DROP TABLE and DROP COLUMN, returned already commented out. Pasting the script whole cannot run them; uncommenting one is a deliberate act.

A primary-key change appears as a commented sketch rather than a statement, because dropping a constraint needs its name and a column diff does not carry one.

TupleNest generates the script and never executes it. There is no run button. Copy it, read it, edit it, and run it wherever you normally run migrations.

Import & export

Import CSV with header mapping and a type/error preview before committing. Export to CSV, JSON, or Markdown. CSV export is spreadsheet-safe by default (formula injection neutralized); a toggle enables raw output.

Importing a file bigger than memory

The file is streamed rather than loaded, so its size is not bounded by RAM: a 358 MB CSV of 6,000,001 rows imports with roughly 15 MB of peak memory growth. Only one batch of rows is held at a time.

The preview reads the first 500 rows — enough to map headers and infer types — which is why a large file says "first 500 rows sampled" rather than a total. Progress during the import is the percentage of the file read, because the row count genuinely is not known until it has been read; the count in the final message is what was actually inserted. Cancel during an import stops the read and rolls the transaction back.

Pages

History, Saved queries, Dashboards, Notebooks, Backup and restore, and Users and roles each take the editor's place; the editor stays open behind them. Every page has the same header — ← Editor, the title, a line saying what it is, and its actions — and Esc goes back from any of them. Open them from the left rail or the command palette.

  • Dashboards — pin a saved query as a bar, line or single-number chart. Charts re-run when the page opens and, if you choose, every 1, 5 or 15 minutes while the dashboard's connection is live. Only a query that reads can be pinned, and each run keeps 1,000 rows.
  • Notebooks — text, SQL and chart cells. Nothing runs when a notebook opens; a SQL cell runs on its own Run, on the notebook's connection, through the guard and audit log. Each SQL cell keeps its last 200 rows in the local database so the notebook reopens as you left it.
  • Backup and restore (PostgreSQL) — runs your own pg_dump (custom format) and pg_restore, found in a folder you set, on PATH, or in the usual install locations. The password is passed in a private temporary pgpass file, never on the command line. Restoring into prod or staging asks you to type the database name; a read-only profile is never restored into. Profiles that use an SSH tunnel are not supported yet.
  • Users and roles (PostgreSQL) — each role's SELECT, INSERT, UPDATE, DELETE and TRUNCATE on each table of a schema, with a warning when a role that looks read-only can write or is a superuser. Nothing here changes a grant: the matching SQL is shown to copy.

The assistant

Open it from the title bar or with ⌘J. Add a provider in Settings › Assistant: your own Anthropic API key (kept in the OS keychain), or an Ollama server — http://localhost:11434 by default; one on another computer only if you allow it.

A request contains your message and the recent turns of that conversation, the editor's SQL for Ask, Explain and Fix, a failed statement's error with its DETAIL and CONTEXT lines removed, and the connected database's schema, table and column names and types, capped. It never contains row data, history, the connection's host, user or password, or other connections. A suggestion runs only when you insert it and press Run. The full list is in PRIVACY.md.

MCP server

Start the app as tuplenest-desktop mcp from an AI tool (Claude Desktop, Claude Code, Cursor); Settings › MCP server shows the configuration with this install's path. Each connection is Off until you set it to Read only or Read and write; Read and write refuses anything the guard would ask about and is not offered on prod, staging or read-only connections. One statement per call, at most 500 rows back, audited first on prod and staging. What a query returns goes to the tool that asked.

Read-only mode

On SQLite, read-only opens the file read-only, sets PRAGMA query_only before every statement, and refuses a statement SQLite says would write.

Turn on read-only for a PostgreSQL connection and TupleNest issues a PostgreSQL read-only session characteristic — the server refuses writes, not just the UI. TupleNest also sends only statements that read, because the server's read-only mode would still run VACUUM, ANALYZE, CHECKPOINT and COPY … TO PROGRAM. A function with a side effect called from a SELECT is not stopped. It's an accident guardrail; for strict enforcement, use a database role without write privileges.

Dangerous statements

On connections tagged prod or staging, statements like DELETE/UPDATE without a WHERE, or DROP/TRUNCATE, trigger a confirmation. The check masks comments and strings first, so a commented-out WHERE can't disarm it.

Security & privacy

No telemetry, no account, no cloud. The only network destinations are your PostgreSQL host, your SSH host (if configured), the GitHub update endpoint, and the assistant's model if you set one up and ask it something. The full model is on the Security page.

Settings

Settings has a section list: General (appearance, results, privacy and updates), Assistant, MCP server, Shortcuts and About. General holds the theme and the telemetry switch, and shows two fixed limits: explorer-generated SELECTs use LIMIT 100, and history keeps the newest 1,000 statements (favourites are never dropped). The audit log keeps the newest 5,000. Neither limit is configurable yet, and the update check at startup cannot be turned off.

Troubleshooting

  • Cannot connect — run Test to see which stage fails (DNS, TCP, or auth).
  • TLS certificate failure — check the mode and, for a private CA, set the custom CA path.
  • SSH host-key failure — the key changed; verify with your admin before trusting it.
  • Keychain access error — grant TupleNest keychain permission when the OS prompts.
  • Query timeout / large result — adjust the statement timeout or narrow the query; the grid keeps the first 20,000 rows (or 128 MB) and says when it has stopped; those limits are fixed. Copying rows to the clipboard takes at most 10,000 at a time; export to a file for more.
  • Update failure — betas update by manual download; the auto-updater targets stable releases.
  • Logs — rotating log files live in the app-data directory, under the bundle identifier rather than the product name: ~/Library/Application Support/app.tuplenest.desktop/logs on macOS, ~/.local/share/app.tuplenest.desktop/logs on Linux, %APPDATA%\app.tuplenest.desktop\logs on Windows. Owner-only on Unix.
  • Checking a Windows build by hand — CI installs the .msi and confirms a window opens, but cannot drive the UI on Windows (a release build has no WebView2 debugging port). There is a twelve-step manual check for the rest.
